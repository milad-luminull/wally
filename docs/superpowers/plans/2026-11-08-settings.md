# Settings Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One Settings area that looks like the board (rail on the left, section on the right),
reached from a Settings item in the board rail, the profile popover and the command palette,
with Back returning to the page it was opened from.

**Architecture:** A new `features/settings/` module holds the shell (rail on desktop, list on
narrow screens), the section registry, a small origin helper that carries "where I came from"
in router location state, and one component per section. The board rail's CSS classes are
widened to cover links so the Settings rail reuses them verbatim; a new `settings.css` holds
the content rows. The web app only changes; the API is untouched.

**Tech Stack:** React 19, React Router 7 (`react-router`), Tailwind plus plain CSS in
`src/styles/`, i18next catalogues (`src/i18n/en.ts`, `de.ts`), lucide-react, Vitest +
Testing Library, Playwright.

**Spec:** [docs/superpowers/specs/2026-11-08-settings-design.md](../specs/2026-11-08-settings-design.md)
— read it first. Its **Visual spec** table and sketches are the source of every pixel value.

## Global Constraints

- English identifiers, test data and copy keys; German only in `de.ts` (ADR-0014).
- Every user-visible string goes through i18next; `noHardcodedCopy.test.ts` must stay green.
- Only semantic tokens (`--rail`, `--inset`, `--inset-hover`, `--surface`, `--canvas`,
  `--fg-1`, `--fg-2`, `--fg-3`, `--fg-faint`, `--border-subtle`); no palette-specific code.
- Focus is a 2px `--fg-1` outline with 2px offset, never the accent.
- No new dependencies, no API change, no change to how preferences are stored.
- The signed-out landing page (`PublicHeader` → `AppearanceControls`) must render exactly
  as before.
- `/settings/account` and `/settings/connections` keep working.
- Breakpoint: `useBreakpoint().isDesktop` (≥1080px) shows the rail; below it, the list.
- jsdom's default `innerWidth` (1024) is _tablet_: tests that need the desktop layout mock
  `@/lib/useBreakpoint`.
- Targeted unit runs on the host: `pnpm -C apps/web exec vitest run <file>`. Full suite:
  `make test`; also `make lint` and `make typecheck`.
- E2E runs only in CI (never trust a local green run). Nothing is pushed until the owner has
  reviewed the branch locally.

## Review Focus

1. **Origin is a settings page or garbage** (`state.from` is `/settings/language`, `//evil.com`,
   `https://x`, a number) → Back goes to `/boards`, never loops or leaves the site. Pinned in
   Task 2.
2. **Reload or opening a link in a new tab** loses location state → Back still works (goes to
   `/boards`). Pinned in Task 2 and Task 4.
3. **Resizing across 1080px while in Settings** → on `/settings` the list becomes a redirect to
   Appearance (and vice versa) without losing the origin. Pinned in Task 4 (redirect carries
   state).
4. **Opening a section directly on a phone** (`/settings/account` from a bookmark) → "← Settings"
   goes to the list, not out of the app. Pinned in Task 4.
5. **Account deletion from the new page** → the dialog and its after-deletion behaviour work
   unchanged inside the shell, desktop and phone. Pinned in Task 5 (unit) and the existing
   `account-delete.spec.ts` (E2E).
