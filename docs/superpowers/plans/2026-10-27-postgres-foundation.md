# PostgreSQL Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a Drizzle schema, migrations, a local PostgreSQL, a per-file test harness, a pooler-safe client and a serializable transaction helper to `apps/api`, used by nothing yet.

**Architecture:** A new module `apps/api/src/lib/postgres/` holds the client, the schema (one file per aggregate), the migration runner, the error classifier and `withTransaction`. Migrations are generated by drizzle-kit into `apps/api/drizzle/`. A Vitest global setup migrates a template database once; each test file clones it. The API keeps running on Firestore and nothing outside the module and its tests imports it.

**Tech Stack:** drizzle-orm 0.45.4, drizzle-kit 0.31.11, postgres (postgres.js) 3.4.9, `supabase/postgres:17.11.0.003`, Vitest 3, Docker Compose, GitHub Actions.

**Spec:** [docs/superpowers/specs/2026-10-27-postgres-foundation-design.md](../specs/2026-10-27-postgres-foundation-design.md)

## Global Constraints

- Branch `feat/postgres-foundation`, cut from `origin/main` after PR #86 is merged; one PR, base `main`. Never switch branches in the main checkout `/Users/mr_user/development/apps/wally`; work in a worktree.
- $0: no hosted Supabase project, no secret, no release workflow change.
- Prepared statements off in every client (`prepare: false`): the Supabase transaction pooler does not support them ([Supabase](https://supabase.com/docs/guides/database/connecting-to-postgres), [Drizzle](https://orm.drizzle.team/docs/connect-supabase)).
- Image `supabase/postgres:17.11.0.003` everywhere (compose and CI), never a floating tag.
- English identifiers, values and test data (ADR-0014). Tables and columns snake_case (Drizzle `casing: 'snake_case'`).
- IDs are `text`. Timestamps are `timestamp({ withTimezone: true })` in `mode: 'date'`. Date-only values are `date({ mode: 'string' })`. Money in micro-USD is `bigint({ mode: 'number' })`.
- No legacy defaults or read shims (clean start).
- Nothing outside `apps/api/src/lib/postgres/` and `apps/api/test/` imports the module (Task 5 adds a test that enforces it).
- Exactly one migration file in `apps/api/drizzle/` when the PR opens: until a hosted database applies it, regenerate rather than stack migrations.
- New dependencies: `pnpm install` on the host, then `docker compose build api`, before `make test` sees them.
- No Playwright spec changes: no user flow changes. The PR says so.
- Before calling the PR ready: push, then read CI with `gh pr checks` (E2E runs only in CI).

## Review Focus

- **jsonb stored as a JSON string** (a known double-encoding trap between Drizzle and postgres.js): an object written to a `jsonb` column must read back as `jsonb_typeof = 'object'`. Test in Task 1.
- **Due dates shifting by a day:** `'2026-03-29'` (a DST change day in Europe) must round-trip unchanged. Test in Task 2.
- **Large micro-USD sums** coming back as strings or losing precision: `5_000_000_000` must read back as the number `5000000000`. Test in Task 3.
- **Timestamps losing their instant:** a `Date` with milliseconds round-trips equal by `getTime()`. Test in Task 1.
- **Running tests without `DATABASE_URL`:** the global setup must not fail the whole run (web and pure unit tests still run), but `createTestDatabase()` must reject with a message naming `DATABASE_URL`. Test in Task 1.

### Task 4: Error classification and `withTransaction`

**Files:**

- Create: `apps/api/src/lib/postgres/errors.ts`, `apps/api/src/lib/postgres/transaction.ts`
- Test: `apps/api/src/lib/postgres/errors.test.ts`, `apps/api/src/lib/postgres/transaction.test.ts`

**Interfaces:**

- Consumes: `Database`, `createTestDatabase()`, the schema.
- Produces:
  - `type DatabaseErrorKind = 'serialization' | 'deadlock' | 'unique' | 'foreignKey' | 'check'` and `function classifyDatabaseError(error: unknown): DatabaseErrorKind | null`. It maps `40001`, `40P01`, `23505`, `23503` and `23514`, reading `code` on the error or on its `cause` (one level).
  - `class TransactionConflictError extends Error { readonly attempts: number }`, with the last failure as `cause`.
  - `type Transaction` (the `tx` Drizzle passes to `db.transaction`).
  - `function withTransaction<T>(db: Database, body: (tx: Transaction) => Promise<T>, options?: { maxAttempts?: number; random?: () => number; sleep?: (ms: number) => Promise<void> }): Promise<T>`. It runs `db.transaction(body, { isolationLevel: 'serializable' })`. On `serialization` or `deadlock` it waits `random() * min(200, 10 * 2 ** attempt)` ms and runs the whole body again, up to `maxAttempts` (default **5**). Then it throws `TransactionConflictError`. Any other error is rethrown at once, unwrapped.

- [ ] **Step 1: Write the failing tests.**
  - `errors.test.ts` triggers real errors through Drizzle on a test database: a duplicate `users.id` gives `'unique'`; a `notes.board_id` naming no board gives `'foreignKey'`; a bad note `status` gives `'check'`. `{ code: '40001' }` gives `'serialization'`, `{ cause: { code: '40P01' } }` gives `'deadlock'`, and `new Error('x')` gives `null`.
  - `transaction.test.ts`:
    - `runs the body at serializable isolation`: inside the body, `select current_setting('transaction_isolation')` returns `'serializable'`.
    - `retries a serialization failure and then succeeds`: the body throws `Object.assign(new Error(), { code: '40001' })` on calls 1 and 2 and returns `'ok'` on call 3. The result is `'ok'`, the body ran 3 times, and `sleep` received 2 waits, each within its cap.
    - `gives up after five attempts`: the body always throws `40001`. It rejects with `TransactionConflictError`, `attempts` is 5, and the body ran 5 times.
