# Project setup

## Monorepo

- pnpm workspaces + Turborepo. One `package.json` at the root, one per package.
- Layout:

  ```
  apps/api          backend
  apps/web          frontend
  packages/shared   types, Zod schemas, constants used by both apps
  packages/config   shared eslint, tsconfig, prettier
  ```

- New code goes into the matching package. Do not create top-level folders without asking.

## Backend (TypeScript)

- Node 22, Fastify, PostgreSQL through Drizzle ORM and postgres.js. firebase-admin is used only to verify Firebase ID tokens.
- Zod schemas live in `packages/shared` and are reused for API validation.
- Change trigger: use Python (FastAPI, SQLAlchemy, Pydantic) only if the app needs heavy data or ML libraries. Keep the same folder layout and share types via an OpenAPI spec.
- The database is Supabase PostgreSQL, reached only through the API ([ADR-0020](adr/ADR-0020-supabase-postgres-through-the-api-with-drizzle.md), plan in [RFC-0011](rfcs/RFC-0011-platform-migration.md)). Production still runs v0.11.0 on Firestore until the release that ships this code ([DEPLOY.md](DEPLOY.md)).
- The schema is in `apps/api/src/lib/postgres/schema/`: 19 tables, each with Row Level Security enabled and no policies. Row types are in `apps/api/src/lib/db/types.ts`, and the loaders in `apps/api/src/lib/db/records.ts` compute what Firestore cached (a board's member roles and share-link token, a note's subtask summary) when they read.
- Every write runs in `withTransaction` (`apps/api/src/lib/postgres/transaction.ts`): SERIALIZABLE, run up to five times with a jittered backoff after a serialization failure or deadlock, as PostgreSQL expects ([transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html)). Its body may run more than once, so it must have no effects outside the transaction. Reads that need one consistent view use `withSnapshot`, a read-only REPEATABLE READ transaction.
- Prepared statements are off everywhere, because production connects through Supabase's transaction pooler, which does not support them ([connecting](https://supabase.com/docs/guides/database/connecting-to-postgres)).

## Frontend (React)

- Vite, React 19, TypeScript, React Router, TanStack Query.
- UI: shadcn/ui on Tailwind CSS. Use its components as the base for every screen. Do not hand-write components that shadcn already provides.
- Change trigger: switch to MUI only if the client requires Material Design.
- i18n: react-i18next. Message catalogues live in `apps/web/src/i18n/` (`de.ts` is the key
  authority, `en.ts` is held to its key set by `resources.test.ts`). Keys are English and name
  the string's role (`.label`, `.aria`, `.body`), never its content. No user-facing string
  belongs in a component — `noHardcodedCopy.test.ts` fails the build if one does. Anything
  held in React state is stored as a KEY and translated at render, or it goes stale on a
  language switch. `packages/shared` keeps the enum VALUES; their labels are web-only.

## Commands

All commands run inside Docker, except `make format` and `make e2e`, which run on the host
with Node and pnpm (Playwright needs browsers the dev containers do not have; CI runs it the
same way). The stack itself needs only Docker and `make`.

| Command          | Purpose                         |
| ---------------- | ------------------------------- |
| `make up`        | Build and start the whole stack |
| `make down`      | Stop and remove containers      |
| `make logs`      | Follow logs of all services     |
| `make test`      | Run all tests                   |
| `make lint`      | Run lint                        |
| `make typecheck` | Run type checks                 |
| `make seed`      | Load development seed data      |

`make up` is the only command a new developer needs.

## Docker

- One `docker-compose.yml` at the root. Services: `postgres` (Supabase's PostgreSQL image, [ADR-0025](adr/ADR-0025-local-postgres-and-per-file-test-databases.md)), `migrate` (applies the migrations once with `pnpm --filter @wally/api db:migrate`, then exits), `api` (starts only after `migrate` succeeded) and `web`, plus any other dependency (redis, mailpit, etc.). There is no Firestore emulator.
- `postgres` publishes no port. Open a shell with `docker compose exec postgres psql -U postgres -h localhost`. Its data lives in the `postgres-data` volume and survives `make down`; `docker compose down -v` deletes it.
- Migrations live in `apps/api/drizzle/`: `0000_initial_schema.sql`, generated by drizzle-kit, and `0001_purge_expired.sql`, hand-written, which holds the `purge_expired()` function and its hourly Supabase Cron job. A schema change: edit `apps/api/src/lib/postgres/schema/`, then write a new migration with `pnpm --filter @wally/api db:generate --name <change>`. SQL that drizzle-kit cannot express (functions, cron jobs) goes in a custom migration, `pnpm --filter @wally/api db:generate --custom --name <change>` ([custom migrations](https://orm.drizzle.team/docs/kit-custom-migrations)). Never delete or rewrite the folder: that would lose the custom migration. Every migration must keep working with the API revision still serving ([DEPLOY.md](DEPLOY.md), section 7).
- `pnpm --filter @wally/api db:migrate` applies the migrations; compose's `migrate` service runs it before the API starts.
- `docker-compose.mcp-local.yml` is a separate stack with its own `postgres` and `migrate` ([AUTH0.md](AUTH0.md#local-mcp-run)).
- `DATABASE_URL` is required. The E2E and local MCP fixture seeds refuse any `DATABASE_URL` whose host is not `localhost`, `127.0.0.1`, `[::1]` or `postgres`, and any `NODE_ENV=production`. The demo seed (`make seed`) has no such guard.
- All dependencies live in compose. Never ask the developer to install or run anything outside it.
- One `Dockerfile` per app, multi-stage: `dev` target with hot reload, `prod` target minimal.
- `.env.example` lists every variable. Compose reads `.env`. Never commit `.env` or write real secret values into the repo.

## Tests

- Backend: Vitest. Unit tests for business logic and validation. Integration tests for each API route against the compose PostgreSQL; `make test` runs them inside the api container. Each test file calls `createTestDatabase()` (`apps/api/test/postgres.ts`) for a database of its own, cloned from a template migrated once per run, and drops it in `afterAll`, so files stay isolated and run in parallel ([ADR-0025](adr/ADR-0025-local-postgres-and-per-file-test-databases.md)).
- Frontend: Vitest + React Testing Library for components with logic (forms, state, conditional rendering). No tests for pure layout components.
- End-to-end: Playwright. One happy-path test per main user flow. No more.
- Test behaviour, not implementation. No snapshot tests. No tests that only check a mock was called.
- Target: every route and every business rule has a test. Do not chase a coverage percentage.

## Working rules

1. **Work in cycles, not one pass.** Plan → build → test → review → fix. Repeat until every requirement is done. At the end of each cycle, list what is done, what is open, and what you will do next. Do not stop while any item is open.

2. **Adapt the workflow to the task.** Do not follow a fixed script. Re-plan when you learn something new. If a requirement is unclear, ask before you build. If you find a gap or conflict, report it; do not fill it with an assumption.

3. **No skipped requirements, no shortcuts.** Before you build, write the full requirement list as a checklist. Every item must be implemented, tested, and marked done before you report completion. A stub, TODO, placeholder, or "can be added later" is not done. Do not remove or narrow a requirement to make it easier.

4. **Design and UX quality is a top priority, equal to correctness.** For every screen and flow: clear hierarchy, consistent spacing and typography, sensible defaults, loading, empty, and error states, keyboard and screen-reader access, responsive layout. Review each UI change as a designer would before you mark it done. If a design decision is not specified, choose the option a strong product designer would choose and explain why.

5. **Verify before you claim.** Run the app, run the tests, and check the UI. Report only what you have verified. If something does not work, say so.

## Git

- Branch names: `feat/<short-name>`, `fix/<short-name>`, `chore/<short-name>`.
- Commit messages: Conventional Commits (`feat:`, `fix:`, `chore:`, `test:`, `docs:`).
- Small commits. Never commit directly to `main`. Never force-push.

## Documentation

- Docs live in `docs/`; start at [`docs/README.md`](README.md) for what goes where.
- A decision that is hard to reverse, changes stored data, or picks between real alternatives gets an ADR in `docs/adr/` (template: `ADR-0000-template.md`, process: [`docs/adr/README.md`](adr/README.md)).
- Never edit an accepted ADR; supersede it with a new one.
- This file holds working conventions. The reasoning behind a convention belongs in its ADR.

## Ask before you do

- Delete files or folders.
- Change the database schema.
- Add or upgrade a dependency.
- Touch authentication, authorization, or payments.
- Change scope or drop a requirement.

## Definition of done

- `make up` starts clean from an empty checkout.
- `make test` and `make lint` pass.
- Types check with no errors.
- No console errors in the browser.
- All requirements from the checklist are implemented and verified in the running app.
